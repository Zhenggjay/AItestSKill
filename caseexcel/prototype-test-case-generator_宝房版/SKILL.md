# 原型测试用例生成器

## 目标

像资深测试人员一样理解完整业务资料，逐页面、逐行为设计可独立执行的测试用例。测试设计完整性不得因最终只交付两个文件而降低；先完成覆盖度审计和补全，最后只导出一次。

## 最终交付契约（硬性）

每个任务最终只能在交付目录中保留以下两个文件：

1. `<功能名称>测试用例-TAPD传统版.xlsx`
2. `<功能名称>测试用例-TAPD测试协同版.xlsx`

必须遵守：

- 两份文件包含同一批最终用例，用户下载后可分别直接导入 TAPD 传统测试用例模块和 TestX 测试协同模块。
- 文件名固定，不加日期、时间戳、轮次、初版、补全版、完整版、最终版或“最终完整版”。同一任务重跑时覆盖同名文件。
- 不交付标准格式 Excel、XMind、Markdown、OPML、JSON、覆盖报告或其他伴随文件。
- 不在工作区的 `tools`、`outputs` 或 `deliverables` 中保存初始用例文件、中间 Excel 或审计报告。
- 中间 JSON 只允许写入操作系统临时目录，或在写入器限制下使用工作区受控 `scratch/`；两份 Excel 校验成功后删除该临时 JSON。
- 只有最终用例集合完成后才能调用导出脚本，整个生成链路只调用一次。

## 工作流程

### 0. 锁定范围并通过原型覆盖门禁

在设计任何候选用例之前，先建立“预期页面清单”和“已采集页面清单”：

- 范围只由用户文字中的明确限制决定。用户未指定页面、目录或模块时，Axure/CoDesign sitemap 中的全部真实页面都属于当前范围。
- 原型 URL 的锚点、当前页、落地页和已有的单页截图都不是范围限制，禁止据此擅自缩小范围。
- 对 Axure，优先读取 `extraction-manifest.json`。全量任务必须满足 `complete=true`、`scope=all`、`selectedPageCount=sitemapUniquePageCount`、`completedAdvancedPageCount=selectedPageCount`。
- 旧采集结果没有 manifest 时，按 sitemap 的唯一页面 URL 与 `pages/` 下包含 `data.json` 的页面逐一比对；不能只比较目录总数。
- 发现缺页时，先调用 `extract-axure-data` 按原范围补齐。无法补齐时停止生成和导出，列出缺失页并请用户确认是否改为部分范围；不得自行声明“范围已确认”，也不得用 sitemap 标题替代页面证据。

通过门禁后，为每个范围内页面记录页面名、模块路径、证据文件和全部独立可测试行为。跨页面流程只能补充端到端覆盖，不能替代各页面自身的展示、操作、校验和状态用例。若页面确无独立可测试行为，必须记录具体理由和证据路径，不能静默零覆盖。该清单写入临时 JSON 的 `coverage_scope`，仅用于审计，不导出到 Excel。

### 1. 读取完整资料

- 检查当前工作区内的截图、原型解析结果、需求文档、页面树、页面文本、交互、注释和已有测试资料。
- 如果存在 Axure/CoDesign 的完整采集结果，不能只看摘要或单张截图。
- 按预期页面清单逐页读取证据，不能读取一个页面后就开始生成整个原型的用例。
- 识别页面/模块、角色权限、状态流转、字段规则、操作反馈、上下游关系和明确的非功能要求。
- 不得把原型中没有证据的业务规则写成确定事实；必要假设应体现在前置条件或测试数据中。

### 2. 设计候选用例

#### 2.1 逐页面建立行为清单

对每个可测试页面逐项识别，不得只写页面摘要：

- 默认展示、数据来源、空数据、加载中、失败和刷新状态。
- 每个按钮、链接、标签、筛选、分页、选择、展开、关闭、确认、取消、编辑、删除和批量操作。
- 每个表单字段的必填、格式、长度、数值、时间、选项和字段联动规则。
- 每个业务状态及允许转换、非法转换、重复操作和并发冲突。
- 页面间导航、数据回显、跨页面一致性和端到端主流程。
- 未登录、角色不足、越权访问、租户/用户数据隔离和敏感信息展示。
- 需求明确提出的性能、安全、兼容性、稳定性要求。

只为原型、注释、交互或需求中存在及可合理推导的行为生成用例；没有上限证据时不要编造具体数值上限。

#### 2.2 原子化拆分（硬性）

满足任一条件时必须拆成不同用例：

- 操作命令不同，例如确认、取消、编辑、删除、关闭。
- 前置业务状态或目标状态不同。
- 成功、校验失败、依赖失败、权限拒绝或恢复路径不同。
- 测试数据属于不同等价类或边界点，且可能独立通过或失败。
- 任一预期结果可以在其他预期仍成功时单独失败。

只有前置条件、操作路径和验证目标完全相同，仅替换无业务差异的代表值时才允许参数化合并。禁止把多个按钮、多种状态或多个独立业务目标塞进一条用例。

#### 2.3 按行为生成场景

对每个独立行为至少生成一条主成功路径，并按证据和风险补充：

- 表单：合法提交；必填字段为空；有明确格式/长度/范围时覆盖有效、边界和越界；取消与重复提交分别验证。
- 列表/卡片：正常数据、空数据、加载/刷新，以及原型中存在的搜索、筛选、排序、分页、全选和批量操作。
- 弹窗/面板：打开、数据回显、每个确认类操作、每个取消/关闭方式及提交校验。
- 状态流程：每个允许转换分别覆盖；补充非法转换、终态重复操作和关键并发冲突。
- 删除/不可逆操作：未选择、确认、取消、成功后的数据一致性，以及需求支持时的失败恢复。
- 权限与隔离：按角色、资源归属或租户边界分别验证；一条全局安全用例不能替代高风险页面的权限场景。
- 跨页面流程：覆盖关键业务闭环，但不得用一条端到端用例代替沿途页面的局部功能用例。

#### 2.4 数量与质量门禁

- 每个可测试页面至少包含 3 条页面级用例，并同时覆盖“正向/展示”和至少一个“异常/边界/状态/权限/安全”维度。这是低覆盖警戒线，不是目标数量。
- 页面存在多个独立行为时，用例数必须随行为和适用风险增加，不能为了贴近 3 条而合并行为。
- 纯说明、本期不做或没有独立交互的页面可标记 `testable=false`，但必须给出具体原因和证据路径。
- 不为了凑数量复制相同场景，不为没有证据的字段限制或后台故障编造用例。
- 标题应描述行为与结果，不使用“场景一”“测试一下”等空泛名称。
- 步骤只写操作，预期结果写可观察结果；测试数据必须具体可用。

### 3. 写入临时候选 JSON

优先在操作系统临时目录创建 JSON；若工作区写入器禁止目录外写入，则使用当前工作区受控的 `scratch/`，且不得写入 `outputs/` 或 `deliverables/`。结构如下：

```json
{
  "filename_prefix": "租户管理测试用例",
  "creator": "测试人员",
  "coverage_scope": {
    "pages": [
      {
        "page": "租户列表",
        "testable": true,
        "evidence": "pages/租户列表/data.json",
        "behaviors": ["默认列表展示", "打开新建租户表单", "按名称搜索租户"]
      },
      {"page": "术语说明", "testable": false, "reason": "该页仅提供术语说明，没有独立交互", "evidence": "pages/术语说明/content.md"}
    ]
  },
  "test_cases": [
    {
      "用例编号": "TC-001",
      "用例标题": "管理员成功创建租户",
      "用例目录": ["租户管理", "新建租户"],
      "所属模块": "租户管理",
      "优先级": "P0",
      "前置条件": ["管理员已登录", "租户名称未被占用"],
      "测试步骤": ["进入新建租户页面", "填写合法租户信息并提交"],
      "测试数据": ["租户名称：自动化租户001"],
      "预期结果": ["提交成功", "租户列表出现新租户且状态正确"],
      "用例类型": "功能测试",
      "来源页面": ["租户列表"],
      "测试维度": ["正向", "表单"],
      "场景层级": "页面",
      "覆盖行为": "打开新建租户表单",
      "需求ID": [],
      "标签": [],
      "关联需求": []
    }
  ]
}
```

字段规则：

- `用例标题` 必填；`优先级` 只能是 `P0/P1/P2/P3`。
- `coverage_scope.pages` 必须覆盖当前范围全部页面；`page` 使用 sitemap/manifest 的原始页面名。每个可测试页面必须填写 `evidence`，并在 `behaviors` 中逐项列出该页全部独立可测试行为。
- 每条用例必须填写 `来源页面`、`测试维度` 和 `场景层级`。`场景层级` 只能是“页面”或“端到端”；这些审计字段不会写入 TAPD Excel。
- 页面级用例必须且只能关联一个来源页面；跨页面流程使用“端到端”层级，并在 `测试维度` 中包含“端到端”。
- 每条页面级用例必须用 `覆盖行为` 指向来源页面 `behaviors` 中的一个原子行为。每个行为至少被一条页面级用例覆盖；不得用一条用例同时认领多个独立行为。
- `测试维度` 从“正向、展示、导航、表单、异常、边界、状态、权限、安全、性能、兼容性、稳定性、端到端”中选择一个或多个。
- `用例目录` 推荐使用字符串数组表达层级；导出器会分别转换为传统版的 `-` 和测试协同版的 `/`。
- `需求ID` 仅用于传统模块，可填一个或多个本项目 TAPD 需求 ID。
- `关联需求` 仅用于测试协同模块，应填 TAPD 需求 URL；多个 URL 由导出器用英文分号连接。
- `步骤描述类型` 通常不必填写。导出器仅在步骤与预期逐条对应时使用“步骤”，否则自动使用合法的“文本”类型。
- `创建人` 不写入单条用例；通过导出命令的 `--creator` 统一传入。
- `filename_prefix` 和 `creator` 必须写在 JSON 根对象中。Windows 下不要把中文前缀或创建人作为命令行参数传递，以免受终端代码页影响。
- 临时 JSON 优先写入操作系统临时目录；若工作区写入器禁止目录外写入，可使用当前工作区受控的 `scratch/`，导出成功后必须删除。

### 4. 导出前执行覆盖度审计

候选 JSON 完成后，立即使用 `testcase-gap-filler` 对候选集合做逐页面、逐行为审计和补全。必须在第一次 Excel 导出之前完成，不能先导出初版再补全。

审计结束后继续使用同一个临时 JSON，其中只保留去重后的最终用例集合。必须运行 `testcase-gap-filler/validate_coverage.py` 并通过页面覆盖门禁；失败时返回步骤 2 补全，禁止导出。

### 5. 一次性导出两份 TAPD Excel

将 `<skill-dir>` 替换为本 Skill 所在目录的绝对路径，将输出目录固定为当前任务唯一的 `deliverables` 目录：

```bash
python "<skill-dir>/test_case_exporter.py" --input "<临时目录>/test_cases.json" --output "<workspace>/outputs/<task-slug>/deliverables"
```

导出脚本会：

- 基于 `templates/tapd_traditional_template.xlsx` 生成传统版，删除模板中的字段说明行，仅保留表头并从第 2 行写入用例；“创建人”字段固定为空，由 TAPD 导入时处理。
- 基于 `templates/tapd_testx_template.xlsx` 生成测试协同版，替换示例行、保留“使用说明”工作表并从第 2 行写入用例。
- 校验表头、必填字段、枚举值、用例数量以及测试协同步骤/预期的对应关系。
- 只生成两份固定名称的 `.xlsx` 文件。

如果用户没有指定创建人，使用“测试人员”。

### 6. 清理并回复

- 两份 Excel 均成功生成并通过校验后，删除临时 JSON。
- 最终回答只需简短说明用例数量和审计补全重点，并列出两份 Excel 的下载路径。
- 不把诊断报告另存为文件，不列出中间文件，也不要再次生成其他格式。

## 优先级

- `P0`：阻断核心业务、关键权限或数据安全的场景。
- `P1`：重要业务分支、主要异常和高风险边界。
- `P2`：一般功能、次要异常和常规兼容性场景。
- `P3`：影响较低的极端边界或体验细节。

## 完成检查

- 已锁定用户要求的范围，并通过原型采集覆盖门禁；没有因 URL 锚点或当前页缩小范围。
- 已逐页面枚举独立行为；确认、取消、修改、删除及不同状态转换没有被错误合并。
- 每个可测试页面至少有 3 条页面级用例且覆盖正向与风险维度；复杂页面已根据独立行为继续增加。
- 已读取与当前范围相关的完整资料。
- 每条用例都有明确标题、可执行步骤和可观察预期。
- 已由 `testcase-gap-filler` 完成导出前审计，且 `validate_coverage.py` 校验通过。
- 只调用一次 `test_case_exporter.py`。
- 交付目录中本任务只新增或覆盖两份固定名称的 TAPD Excel。
- 没有生成 XMind、标准版、初版、完整版、最终版、JSON 或 Markdown 交付物。
